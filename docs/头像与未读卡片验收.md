# 头像与未读卡片验收

日期：2026年10月28日。开发分支：`codex/avatars-unread-cards`。实现与维护位置见[头像与未读卡片](头像与未读卡片.md)。此前工作台与WebSocket改造已经完成，本轮继续补齐客户卡片、50张头像库和数字未读。

## 自动验证

- 前端TypeScript、Prettier及55项Node测试通过，包括头像多选/单选、不导出危险头像路径、头像桥不带凭证、撤回及越权目标拒绝、错误媒体类型及超量拒绝、下载后权限复核。
- Go全包测试与`go vet ./...`通过。聊天、身份、装修与平台包的`-race`测试通过，聊天和身份使用真实PostgreSQL独立随机schema。
- 真实头像集成覆盖平台50项清单、普通成员与管理员权限、跨租户资源拒绝、上传重编码、公开图片不带元数据、访客随机持久化、明确头像优先、旧空头像原子补选，以及两个慢传挂起时其他上传仍可完成。
- 真实未读集成覆盖成员各自游标、同编号重试只计一次、公开访客消息置顶、内部备注/心跳/已读不重排、撤回移除未读、跨租户不可见。旁观管理员个人已读不产生面向访客的接待客服已读事件。
- 真实Chromium的SDK测试保留错误nonce、协议版本和发布号拦截；合法专用MessageChannel中的`getAvatar`返回真实PNG Blob，验证类型、大小及文件签名。
- 最终完整应用镜像构建及26项容器HTTP检查通过。50张内置PNG逐张返回200；均为256×256、50个独立SHA，总计4,409,160字节，最大单张105,712字节。图库51张图片（含1张演示上传）全部实际加载。

迁移018、019已经应用到本机独立GoodChat数据库。未新建数据库或Redis容器，未修改其他项目。

## 实际页面验证

以下操作使用本机完整应用、真实API与持久数据库，数据名称均标记“演示数据”。

| 场景 | 实际结果 |
| --- | --- |
| 未读置顶 | 查看乙时向甲保存新消息，甲移动到列表首位，红底白字数字由1到2 |
| 刷新保留 | 刷新工作台后仍为2，点击并实际展示最新消息、收到服务端确认后归零 |
| 实际可见已读 | 记录6次已读请求，页面均可见，实际距底最大0.5px；长会话初次定位和新增消息均未提前上报 |
| 上翻历史 | 保持上方阅读位置收到新消息，未读保留1；滚回底部才归零 |
| 隐藏事件分支 | 在浏览器注入可见性变化事件模拟hidden，真实保存消息并验证未读保留；恢复visible后清除。此项是模拟分支，不能称为实际后台或合盖验收 |
| 卡片样式 | 实际计算样式为12px圆角、左右12px间距、浅蓝`rgb(234,242,255)`选中；状态行只有在线/离线及手机号 |
| 头像池 | 实际多选两张并保存，新客户只取该集合；带同一访客凭证复访保持头像 |
| 上传与会员头像 | 文件选择器上传真实图片；保存仅上传图片的访客池，新客户得到该头像；当前会员保存固定头像后页头图片实际加载 |
| 访客两类页面 | 375px原生访客页中客服头像实际可见；已发布的标准组件装修页通过Blob加载客服头像，图片CSP仍为`img-src data: blob:` |
| 手机页面 | 375×812的头像设置、咨询列表和聊天无页面横向溢出，未读红色数字实际显示 |

浏览器复检修复了两个关联问题：先等真实末尾布局连续两帧再上报已读，避免平滑滚动途中清零；消息异步加载完成后重新定位，避免仍停在加载前位置。租户头像池的默认标记改为遵守后端`using_defaults`，个人已读事件也限定正确的对方身份类型。

自动化浏览器的多个标签可能同时报告visible，生命周期冻结请求也未可靠阻止页面任务，因此本轮没有把这些命令称为真实后台、完整冻结或物理合盖的证明。真实设备长时间后台、合盖与生产网络验收仍是独立边界，已经入库的消息恢复依旧由持久事件补拉保证。

本机截图、检查日志和私有脚本位于`.local/evidence/avatars-unread/`，认证与访客凭证不提交仓库。

验收后已结束4条演示咨询、停用2个演示链接，恢复原租户头像池、个人头像与上下班/忙碌设置并重新读取核对。演示聊天历史、头像上传和标记为演示数据的页面保留用于复查，没有覆盖原链接或业务配置。
