# 实时连接真实并发压测

工具入口是 `scripts/realtime-load.sh`，复用后端现有 Go 模块中的 coder/websocket 与 pgx，不安装 k6 或新依赖。源码分为夹具、真实传输、资源采样与阶段运行。默认仅50条真实WS，显式阶梯才会继续。

## 运行前提与夹具

只允许 `http://127.0.0.1:端口` 及显式本机 `goodchat_saas` 私有迁移连接。默认从 `.local/dev-database.json` 读取，配置和错误不得打印DSN。新夹具会新建名称以“演示数据·实时”开头的独立租户、不可密码登录的测试账号及1天期真实Cookie，复制当前免费基础功能到一个新的非公开零价测试套餐，仅调整该夹具席位；不修改免费套餐、原租户、平台容量基线或全局限流，不发送邮件。

```sh
scripts/realtime-load.sh --mode fixture --agents 5 --visitors 400 \
  --label 压测 --fixture .local/evidence/realtime-resilience/load/fixture.json
```

`fixture.json` 和 `owner-auth-state.json` 为0600私有文件，包含认证信息，禁止提交或贴出。生命周期测试使用另一个夹具目录、1位owner与0个预置访客，避免压测占用其接待资格。Cookie必须为32字节随机值的43字符Base64URL；访客凭证另加 `v_` 前缀。

400个访客身份及排队咨询仅由夹具预置，绕开同IP每分钟30次公开建访限制所需的13分钟准备时间。这不是注册/路由入口压测，也不是伪造负载：正式阶段仍通过实际运行服务的Cookie/Bearer鉴权、Redis限流、HTTP人工领取、一次票据消费、真实WS与真实消息事务。所有咨询接待归属由HTTP领取形成，未直接写入人工消息或可靠事件。

## 实际负载与对账

```sh
scripts/realtime-load.sh --mode run --stages 50 --rate 10 \
  --fixture .local/evidence/realtime-resilience/load/fixture.json \
  --output .local/evidence/realtime-resilience/load/final-run
```

50条总WS为5个独立客服与45个独立访客。100/200/400分别为5+95/195/395，不用同一身份的标签页冒充在线人数。持续读取控制帧以响应服务端Ping，等待真实ready后才算建立；末尾再检查活连接数和异常断开，至少覆盖两次15秒服务端探活。

每个访客都通过HTTP发出一条真实公开消息，并收到当前正式客服的公开回复。约10%的访客消息以同一固定编号同时发起两次POST，比较返回持久ID及PG唯一行。约10%访客先获取服务端签名游标，再主动断开WS；离线期间客服保存新回复，访客申请并消费全新票据重连，再用断线前游标补拉。每阶另验证一个已消费票据不可复用（预期401不计作业务故障）。

阶段结束给outbox最多20秒排空，然后按实际接收身份分别遍历HTTP持久events，与WS稳定编号集合合并；再用HTTP消息历史及PG `messages` 行独立对账。HTTP ACK、原始WS收到、原始WS重复、WS+events缺失、HTTP历史缺失、PG缺失和重复分别报告，不能用数据库有行冒充实时已收到，也不能把传输的至少一次语义声称成绝不重复。异常情况下仍以明确失败结果停止升阶。

每阶段JSON记录HTTP/连接/消息保存/实际WS接收的p50/p95/p99（毫秒）、样本数、HTTP状态、唯一消息吞吐、活连接、重连与旧游标补齐数量、容器采样、应用镜像ID。吞吐按唯一业务消息计算，并发幂等重试不重复计入。分位数采用最近秩，不能平均各阶段p95。

## 预算与停止条件

- 生成器 `GOMAXPROCS=2`，Go内存软限384MiB，消息平均不超过10请求/秒；重试对在预留两个速率名额后同时发起，允许2请求瞬时突发。票据建立为12/秒，保持现有Redis规则有效。
- 只读 `docker stats goodchat` 每3秒采样。CPU以单核100%口径超过400%连续3次、容器内存超过1.2GiB、生成器堆超过384MiB，立即取消当前负载。
- HTTP错误超过2%（至少20请求），或消息保存p95超过2秒（至少20样本），取消当前阶段。未响应或损坏的200正文也算失败，不能记为成功。
- 阶段结束要求接收p95不超过2秒、排空后outbox为0、无非预期断连，才判实时交付质量通过。这是此次明确测试门槛，不是行业标准。
- 数据完整性与交付质量单独列出；任一不通过就不自动升到下一阶。可用 `--stages 50,100,200,400` 显式执行，但先审核资源预算与上一阶证据。默认不自动跑400。
- Ctrl-C/SIGTERM取消当前阶段并关闭自身WS。物理睡眠与正式压测互斥，不能把本机服务随Mac一起暂停的场景当作远程服务仍在线。

Go软内存限不等于操作系统硬隔离，工具不会自行更改应用容器配额，避免影响同机其他验收。资源超限和终止的报告不应当成成功阶段。

## 清理及结果限制

```sh
scripts/realtime-load.sh --mode cleanup \
  --fixture .local/evidence/realtime-resilience/load/fixture.json
```

只处理夹具中已验证名称和编号的新租户：动态安全枚举该测试tenant全部queued/assigned/active咨询（包括浏览器后来创建的咨询），逐HTTP canonical `/assignments/close`确认返回closed，PG核对未结束和current_load均为0后，才禁用入口/成员、撤销对应登录会话、停用新私有套餐并将租户停用；保留消息记录供审计。不操作生命周期夹具，直到其验收完成。

本机共享Docker VM、PG和Redis，生成器也在同一Mac，父任务可能有少量独立浏览器流量。记录环境和镜像，不把空闲连接峰值当成业务容量；即使400条WS能建立，也只说明所述文本频率、重试、重连及消息大小下的结果，不外推媒体、AI、多实例、生产网络或长期稳定容量。平台人工压测基线需要管理员另行审核记录，工具不会自动写入。
